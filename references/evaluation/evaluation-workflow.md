# 评估模式工作流（Skill / 插件 / 工具值不值得装）

评估对象：链接、文章、GitHub 仓库、Gist、本地文件或 Obsidian 笔记里介绍的 skill / 插件 / MCP / CLI / 工具。
产出：一份「装不装」的决策报告，必须结合当前用户画像（获取方法见 [user-profile.md](user-profile.md)，不是作者示例 [user-profile.example.md](user-profile.example.md)）。

阅读工具介绍时先做轻量核验：文章主张、官方说明、适用条件和关键缺口。用户要求是否安装、深入评估或对比时，再执行完整源码与扫描流程。按 [claim-verification.md](claim-verification.md) 记录证据层次；官网承诺不算本机实测，文档冲突单独保留。

## 触发识别

在读取模式取得正文后，若正文是「导读壳」（头条/微信/知乎/掘金等聚合平台介绍某工具的文章），或用户明确说"这个值不值得装""适不适配""帮我看看这个 skill/插件""和我已有的重复吗""哪个更好"——切换评估模式。

关键：**穿透壳**。多数链接是中文导读壳，真正要评估的是它指向的 GitHub 仓库 / 官网。从正文里找出项目链接，把评估对象切换成那个仓库/官网。报告注明「来源文章：<壳链接>，实际评估对象：<仓库>」。

## 流程

### 步骤 0：拿到真正的评估对象

- 本地文件 / Obsidian 笔记：直接读文件，跳过抓取；读完仍做壳穿透（0.2）。
- 网络链接：只移除确认不影响资源的纯跟踪参数；保留资源身份、版本或授权所需参数，不能机械截掉整个 query。带签名、token 或私有标识的 URL 不交给新增第三方代理。
- GitHub 仓库优先读：`README.md` → `SKILL.md` → `plugin.json`/`.claude-plugin/marketplace.json` → `package.json` → `.mcp.json`。
- 抓不到（付费墙/反爬/需登录）：按 `fetch-strategies.md` 降级；仍失败则如实说，让用户提供正文或仓库地址，**绝不编造评估结论**。

### 步骤 1：识别「这到底是什么」

| 类型 | 典型信号 | 原生适配？ |
|------|---------|:---------:|
| Skill | 有 `SKILL.md`，含 `name`/`description` frontmatter | ✅ |
| Plugin | `.claude-plugin/` 或 plugin.json | ✅ |
| MCP Server | 提到 mcp add、@modelcontextprotocol | ✅/⚠️ |
| 普通 CLI / Python / npm 工具 | 命令行程序，没提 agent 集成 | ⚠️ 需 skill 包装 |
| 别家平台专属（Cursor/Gemini/Codex） | 只给那些平台安装说明 | ⚠️/❌ |
| 教学课程 / 纯知识 | 没有可安装物 | ❌ 不安装，摘要即可 |

顺带判断「在哪装、在哪用」：CLI-only（要执行脚本/读写本机/装组件/驱动浏览器/登录）vs 两端通用（纯 SKILL.md 文本）。
细节见 `extension-types.md`。

### 步骤 2：三轴评估（每条独立出结论，不混为一谈）

**轴 A：是否值得装（项目客观质量，与用户无关）**
- 维护信号：最近更新时间、版本记录、已知缺陷与修复；版本少或星数低只作背景，不自动等同质量差。
- 可信度：官方/知名社区、star/采用量、文档完整性、源码可读
- 真问题：解决真痛点还是造需求
- 软文自夸数字（"冠军""N 个技能"）一律标**待核实**，不当事实
- 核验关键承诺的模式、账号、费用、数据去向和正文覆盖条件；官方文档不一致时列出双方来源，记录“资料冲突、行为未验证”。
- 结论：值得 / 看情况（列出条件）/ 不建议

**轴 B：是否适合当前用户（先按 user-profile.md 获取用户画像）**
- 获取画像：读 AGENTS.md/CLAUDE.md/用户描述 → 用户本次对话说明 → 记忆库 → 一句话确认 → 通用默认（报告标注"通用假设"）
- 对照画像维度：职业主线 / 学习兴趣 / 工作流与环境 / 硬性偏好 / 平台兼容性
- 画像信息不足时：结论写"暂无法判定（缺画像）"，不臆测用户身份
- 结论：契合 / 部分契合（说清哪部分用不上）/ 不契合 / 无法判定

**轴 C：是否有风险**
- 判断级：供应链（实际安装来源、版本固定、依赖和执行行为）、权限与数据（读什么、外发什么）、维护断供；低星或单作者不直接定为高风险
- 数据流：分别检查本地抓取、Agent 接收、模型推理、遥测与存储；本地运行不代表零外发。区分站点登录态复用、工具账号、远程 API Key 和新增访问权限。
- 内控视角（用户若有审计/内控/合规背景，或画像中体现该要求）：执行 VBA/宏、改活文件、自动提交、改配置权限 → 提示审批链与留痕（segregation of duties / 可审计性 / change control）。画像无此要求时，仍提示高风险动作的可审计性，但不过度强化。
- 外部组件：skill 只是薄壳时，真本事在它调用的外部组件（npx/pip 包、二进制、浏览器驱动、第三方 CLI）。**单独评估那个组件**：来源是否官方、是否提权、是否处理凭证/cookie、是否读敏感数据、是否违反 ToS。vetter 扫不到外部组件，必须单独评并明写。
- 代码级：调用 `scripts/vetter/vett.sh` 扫描（见 [vetter.md](vetter.md)），吸收 BLOCKED/REVIEW/INCOMPLETE/SAFE 裁决；缺扫描器或执行报错不得记为 SAFE
- 结论：低 / 中 / 高，写清主要风险点 + 注明 vetter 裁决（或未执行）

### 步骤 3：查重（用户最在意）

- 已装 Skill：`ls ~/.agents/skills/`、`~/.claude/skills/`、`~/.codex/skills/`，逐个读 description 比对功能
- 已装 MCP / Plugin / CLI：`mcp list`、`plugin list`、`which <tool>`
- 结论：无同类 / 有重叠（点名重叠项）

### 步骤 4：若重叠，对比谁更适合

维度：功能覆盖 / 易用性 / 维护活跃度 / 依赖与成本 / 与用户工作流契合度。
推荐三选一：保留已有 / 换成新的 / 两者共存（分工说明），必须落到具体维度上。

## 输出格式

```markdown
## 📋 评估报告：<候选名称>

**1. 名称/来源**：<原名> — <类型>（来源：<链接/路径>；若穿透过壳：实际评估对象 <仓库>）

**2. 具体功能**：
- <核心功能清单>

**3. 适配哪个 Agent**：
| Agent | 适配? | 安装方式 | 备注 |
|-------|:-----:|---------|------|
| DSH | ✅/⚠️/❌ | … | |
| Claude Code | ✅/⚠️/❌ | … | |
| Codex | ✅/⚠️/❌ | … | |
| Hermes | ✅/⚠️/❌ | … | |
使用面：<CLI-only / 两端通用 / 桌面端>

**4. 宣传是否得到支持**：<已验证 / 有条件支持 / 未验证 / 官方资料冲突 / 有证据反驳>。列出关键主张、来源/日期/版本、适用条件和测试结果；无证据不直接称“虚假”。

**5. 值得装吗**：<值得 / 看情况 / 不建议>（依据：维护信号、可信度、真问题；自夸数字标"待核实"）

**6. 适合你吗**：<契合 / 部分契合 / 不契合 / 无法判定>（依据：按 user-profile.md 获取的用户画像——职业主线、学习兴趣、工作流、偏好、平台；用通用默认时标注"通用假设"）

**7. 有风险吗**：<低 / 中 / 高>
- 判断级：供应链 / 权限与数据 / 内控留痕 / 维护断供
- 外部组件：<它调用/依赖的包·二进制·浏览器·CLI；该组件来源、提权、凭证、ToS 风险>
- 代码级（vetter 裁决）：<BLOCKED / REVIEW / INCOMPLETE / SAFE / 未执行，注明"只覆盖 skill 壳">

**8. 是否已有重复/类似**：<无 / 有（你已装 X，重叠在…）>

**9. 对比推荐**（仅当第8项为「有」时）：
| 维度 | 新候选 | 已装的 X |
|------|--------|---------|
| 功能覆盖 | … | … |
| 维护活跃 | … | … |
| 依赖/成本 | … | … |
| 工作流契合 | … | … |
| 风险 | … | … |
推荐：<保留 X / 换成新的 / 共存分工>，因为<具体理由>

**验证范围**：<实际执行了什么；哪些因工具、授权或材料缺失未执行；安装文件核对、宿主发现、真实调用分别标注，静态检查不替代业务验收>

---
**✅ 最终建议**：<一句话结论；若 vetter 裁决 BLOCKED 则无论前两轴如何都是"不要装">
<若建议装，给可复制安装命令 + 提示"安装前先跑 vetter 扫描">
```

批量场景：先逐项出精简版，最后附汇总表（项目 | 类型 | 适配 | 值得装 | 适合你 | 风险 | 重叠 | 结论）。

## 铁律

- 绝不为凑结论编造（信息不足就说"待核实/信息不足"）。
- 简洁、敢下结论，不堆免责声明。
- 查重和对比是用户最在意的高频诉求，必须做，不能省。
- 安全结论必须含风险提示与外部组件单独评估（高风险动作的可审计性提示不能省）。
- 代码级扫描委派 vetter，不自己造扫描器。
